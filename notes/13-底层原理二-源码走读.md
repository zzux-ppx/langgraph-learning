## 1. 三层架构

```
你的代码                StateGraph (builder)          Pregel (runtime)
────────────           ─────────────────────          ────────────────
add_node/add_edge  →   编译期：拓扑校验、schema       超步循环、任务调度、
invoke/stream      →   →channels/nodes/triggers  →    checkpoint、流式、interrupt
```

`StateGraph` 只是**编译器**；`compile()` 的产物就是一个 `Pregel` 实例
（它本身是 LangChain `Runnable`，所以有 invoke/stream/batch 全家桶）。

## 2. compile() 做了什么（graph/state.py :: compile）

1. **校验**：入口存在性（START 出边）、无孤儿节点、条件边 path 可解析；
2. **schema → channels**：`_get_channels(schema)`：
   - 遍历 `typing.get_type_hints(schema, include_extras=True)`；
   - 有 `Annotated[type, func]` → `BinaryOperatorAggregate(type, func)`（reducer）；
   - 无 → `LastValue(type)`（覆盖语义）；
   - `MessagesState` 的 `add_messages` 本质也是 reducer 函数（含同 id 替换/RemoveMessage 删除）；
3. **包节点**：`attach_node()`，为每个节点造 `PregelNode`：
   - `channels = state 的全部 key`（节点默认读全量 state）；
   - `triggers = [branch:to:<自己>]`（等边来写）；
   - `writers = [ChannelWrite(...)]`（执行后写 state keys + 写控制通道）；
   - 你的函数被包成 `RunnableCallable`，注入 `config`、`store` 等参数
     （**靠函数签名注解做的依赖注入**——所以参数名和类型注解必须对）；
4. **接边**：`attach_edge` / `attach_branch`（笔记 12 §3 的机制）；
5. `Pregel(nodes=..., channels=..., input=..., output=..., checkpointer=..., store=...)`。

**子图的嵌套**：子图节点本身是 Pregel（Runnable），父图把它当普通 proc 执行；
checkpoint 通过 `checkpoint_ns`（命名空间，如 `researcher:task_id`）分层存储，
恢复时框架按 ns 深入子图内部——这就是"子图里的 interrupt 也能恢复"的原因。

## 3. invoke 的主循环（pregel/_loop.py :: tick / _loop）

伪代码（去掉 async/事务细节）：

```python
while True:
    # ① 取当前 checkpoint（含 channel_values/versions/versions_seen/pending tasks）
    ckpt = checkpointer.get_tuple(config) or new_checkpoint(input)
    # ② 算本超步任务（笔记 12 §4 的版本比较 + Send PUSH）
    tasks = prepare_next_tasks(ckpt, ...)
    if not tasks:
        break                              # 没有活跃任务 → 图自然结束
    if step >= config.recursion_limit:
        raise GraphRecursionError
    # ③ 并发执行（线程池/任务组），产出 (task, 写入列表 或 异常)
    for task in tasks:
        try:
            result = task.proc(task.input)          # ← 你的节点函数在这里被调
        except GraphInterrupt: 标记中断，丢弃本任务写入
        except Exception: 若有 error_handler/retry 则处理，否则整图失败
    # ④ 提交写入：应用 reducer、bump 版本、更新 versions_seen
    # ⑤ 写新 checkpoint（每超步一个）；流式 emit（values/updates/...）
    step += 1
```

几个精确的行为结论（读源码 + 实验双重验证）：

- **每超步一个 checkpoint**（所以 `get_state_history` 的快照数 ≈ 超步数 + 输入态）；
- 节点抛异常 → 该超步**所有已执行节点的写入**也作废（超步是事务边界；
  官方错误处理实践：`add_node(retry=...)` 或节点内自愈）；
- `interrupt()` 抛 `GraphInterrupt`：任务写入被丢弃、图停在上一完整超步，
  interrupt payload 存进 checkpoint 的 `pending_writes/interrupts` 结构，
  这就是"暂停"的全部秘密——没有魔法线程，只是"不提交+记录待恢复点"。

## 4. 节点返回值 → State 的路径

```
你的节点 return {"logs": ["x"]}
   │ ChannelWrite._get_updates: dict → [(channel, value), ...]
   │ BinaryOperatorAggregate("logs").update(["x"])   ← reducer 在这里被调用!
   │ channel.logs 版本 +1
   ▼ 下一超步的任意节点 mapper 读取 channels → 组装成 state dict
```

所以 **reducer 的调用时机 = 该节点写入阶段**，而不是"图结束时统一算"。
并发节点各自串行调用同一 reducer（顺序由完成顺序决定）——reducer 必须满足
结合律，结果才与完成顺序无关（`operator.add`/`or_` 满足；不满足就会"看运气"）。

## 5. 值得读的五个源码函数

| 函数 | 文件 | 看什么 |
|------|------|--------|
| `StateGraph.compile` | graph/state.py | builder→Pregel 的完整翻译过程 |
| `attach_edge/attach_branch` | graph/state.py | 边如何变成通道写入 |

每个 debug 事件都能在源码里找到 emit 点。

## 7. 常见源码级 FAQ

**Q: recursion_limit 到底数的是什么？**
超步数。一个超步里跑 10 个并行节点也只 +1。

**Q: 为什么 checkpointer 对 interrupt 是必须的？**
中断的实现=丢弃本任务写入+把恢复点写进 checkpoint。没有 checkpoint，"暂停"无处安放。

**Q: 节点函数的 state 是拷贝还是引用？**
每次从 channels 视图重新组装（mapper），相当于值拷贝——原地改旧对象不影响 channels，
这就是"为什么不该原地修改 state"的机制解释。

**Q: Send 任务的 checkpoint 怎么存？**
Send 写入 `TASKS`（Topic channel），随 checkpoint 持久化；
恢复时 `prepare_next_tasks` 先消费 TASKS 再算 PULL——
所以**含 Send 的图在 Send 之后中断也能恢复**。
